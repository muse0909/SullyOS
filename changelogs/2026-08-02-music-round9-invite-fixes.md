### 4. 搜索排序（江澈转达诉求 2，暮色建议）
- `hooks/useChatAI.ts:3830-3854` 排序策略（暮色 8-2 00:41 确认）：
  1. **精确歌名匹配**优先（去除括号/方括号内容、空格、大小写差异）

## 踩坑 / 关键认知

### music_invite type 复用：成功 / 失败 / 邀请三种场景
- 之前我设计的 type='music_invite' 专给"用户邀请一起听"用
- 现在扩展到 3 种：
  1. **邀请**（user 手动开一起听）：Chat.tsx useEffect 推的 system 消息
  2. **成功回执**（play_song / play_song_and_join 成功）：chatParser 推的 system 消息
  3. **失败回执**（搜不到 / 超限 / 开关关）：chatParser 推的 system 消息
- 三种都走 `[一起听邀请]` 前缀 + 大模型主动引用
- 区别只在 content 文字（成功/邀请是事实描述，失败带"但没找到"）
- 大模型提示词里**检测** "但没找到" 走不同分支

### notifiedListenTogether 必须 add 即使不推消息
- 之前我以为"跳过推消息 = 跳过 add"是合逻辑的（不推就不标记）
- **错**：跳过 add 会让 Chat 重挂载时 useRef 重置 → 误判新开启
- **必须 add**：标记"已通知过"是状态记录，跟"是否推消息"无关
- 教训：module-level Set 用作"已通知"标记时，**任何**通知路径都要 add（无论推不推消息）

### pop 排序 + 不用白名单
- 江澈最初建议"硬编码原唱白名单（周杰伦 / 林俊杰 / 陈奕迅 等）"——暮色 8-2 00:41 否决："维护成本高而且永远漏人"
- 暮色建议"精确匹配 + 按播放量排序"
- 实际 API 返回 `pop` 字段（100=热门, 30=冷门, 0=无数据）
- 精确匹配 + pop 降序 + fee 升序 = 自然选原唱免费版
- **推广**：任何"选最优匹配"场景都该用平台热度字段，不用自维护白名单
