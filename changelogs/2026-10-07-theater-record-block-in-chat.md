# 剧场记录在主聊天里收成一块 —— 能看、能改、能删

**日期**：2026-10-07
**涉及 commit**：`6e51f96e`

## 改了什么

暮色 21:10 提的：剧场的话**塞在上下文里、界面上却看不见**，他没法删，
「上下文里全是剧场乱七八糟的东西，角色已经傻的不行了，没办法测了」。
要的是**剧场记录在主聊天里收成一块，可折叠，能整体删也能单条删**。

### 病根：同一张表，两头各切一刀

剧场的话跟主聊天**存在同一张消息表**里，每条带「来自剧场」的标记
（`useTheaterLive` 入库时写的 `metadata.source = 'theater'`，10-06 第 2 步定的「打标记就天然接上」）。

而两个消费端各切一刀，方向正好相反：

| 位置 | 做法 | 后果 |
|---|---|---|
| `utils/chatPrompts.ts` 组上下文 | **不过滤**，一条条全塞，只加个 `[剧场 第X集]` | 剧场一复读（10-07 实测同一条说三遍）就把上下文占满 |
| `apps/Chat.tsx` 的 `displayMessages` | **明确过滤掉** `source === 'theater'` | 界面上一个字都没有，也就**没有可以点的删除入口** |

两边一拼 = 塞得满、看不见、删不掉。

### 做了什么

1. **`components/chat/TheaterRecordBlock.tsx`（新）** —— 折叠壳
   - 默认收起，标题「剧场记录 N 条」+ 一颗「全删」
   - 展开后每条照常渲染，**长按走主聊天现成的编辑/删除弹窗**（没有另做一套）
   - 「全删」有二次确认
2. **`apps/Chat.tsx`**
   - 单独捞一份剧场消息（`theaterMsgs` state），放在聊天流**最上面**
   - 单条删/编辑同步到这份（不然聊天流那边删不到它）
   - 「全删」走 `DB.deleteMessages(ids)`，**真删，上下文跟着干净**（读的是同一张表）

## 踩坑 / 需要知道的（重要）

- ⚠️ **`char` 是 TDZ 炸弹，我第一版就踩了。**
  `theaterMsgs` 的 state 写在 125 行附近，而 `const char = ...` 在 259 行。
  我顺手在 state 旁边写了 `useEffect(() => loadTheaterMsgs(char?.id), ...)` →
  **运行时会直接崩**（`Cannot access 'char' before initialization`）。
  是 `typecheck` 的 TS2448 逮住的（`npm run build` 照样放行）。
  这次把它挪到 `char` 定义后面，并在原处留了注释。
  **判据：往 Chat.tsx 里插东西，先看插的位置在不在它要用的变量前面。**

- **捞剧场消息必须用 `getMessagesByCharId(id, true)`（带 true）。**
  不带 true 是「只要记忆宫殿还没处理过的」，而剧场每存一条就跑一次记忆宫殿 ——
  他要清的那些恰恰早就被处理过了，用默认参数一条都捞不回来。

- **`MessageItem` 的 props 不要抄第二份。**
  那份清单二十几个字段（语音、翻译、多选、头像尺寸…）。抄一份，以后主聊天加字段就会漏掉剧场。
  做法：抽 `renderMsgItem(m, isFirst, isLast, key)` 一个函数，**主聊天和剧场记录块共用**。

- **位置选「聊天流最上面」而不是按时间插回原位。**
  剧场是对话的旁支不是主线；而且这些消息被记忆宫殿处理过之后，时间轴跟主聊天对不齐，硬插容易错位。
  放最上面 = 一进聊天就看得见、就能清。

- **两边不会重复显示**：`displayMessages` 本来就过滤掉了 `source === 'theater'`，
  剧场消息只从 `theaterMsgs` 那条路出来。

- **`typecheck:theater` 加了新文件**：`components/chat/TheaterRecordBlock`。
  ⚠️ **`apps/Chat.tsx` 故意没加** —— 它带着 10 条历史错误（`Modal` 重复 import、
  `char` TDZ、类型不兼容等），加了这条命令就永远红，等于把命令废掉。
  改 Chat.tsx 时的验证办法：**改动前后各跑一次、按错误内容（去掉行号）diff**，
  确认没有新增。第一次我就是直接对比行号，被行号偏移骗了。
