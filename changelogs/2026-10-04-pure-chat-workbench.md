# 纯聊天模式补全 — 工作台只留核心，省输入 token

**日期**：2026-10-04
**分支**：`fix/amsg2-realign`
**涉及文件**：`utils/chatPrompts.ts`、`hooks/useChatAI.ts`、`utils/chatPrompts.pure.test.ts`（新增）

---

## 这件事的由来

暮色 2026-10-04 说明了这个模式的真实用途：**不是日常聊天，是工作台。**

> 我脑袋有时候不转轴，需要江澈帮我理清思路、给你写更清楚的指令。这个模式我需要用
> 贵的按量的模型，所以要尽量压缩 token。

用途一变，取舍就整个翻过来了：之前是"能省就省"，现在是"输入 token 是真金白银，
能砍就砍"。原来的纯聊天模式只关了 16 项（朋友圈、日程、音乐、Notion…），
**另外 13 项一件没关**，其中包括 tools 数组里那四个常驻描述。

---

## 核心做法：早返回，不是"完整模式减法"

`buildSystemPrompt` 算到纯聊天判定那一行（`chatPrompts.ts:318`）就**直接返回**，
下面的完整路径一行都跑不到。

**为什么不是在那 12 个 `!isPureMode` 上继续加门：**

1. **完整模式是这个 app 日常聊天 + 主动消息走的路，一行都不能动。** 早返回让两条路
   并列而不是串在一起——改纯聊天碰不到完整模式，完整模式出 bug 也跟纯聊天无关。
2. 散着加门会变成 25 处 `!isPureMode &&`，漏一处没人看得见。集中早返回的话，
   "没进请求体的东西"就一个列表（`PURE_CHAT_EXCLUDED`），对着查就行。
3. 顺带把纯聊天路径上所有读 DB、拼 awareness、查音乐、向量检索的开销全省了。

**早返回之后下面那些 `!isPureMode` 的门在运行时已经走不到 pure 了，故意保留**——
删它们等于改完整模式的代码，收益为 0、风险不小。

### 挡在 `buildCoreContext` 内部的那两个

情绪底色（`buffInjection`）和记忆宫殿（`memoryPalaceInjection`）都住在
`buildCoreContext` 里，早返回也躲不掉。解法是**传一份克隆过的角色进去**把字段摘掉，
而不是去改 `context.ts` 的函数签名——那是全局共享函数、五个调用点，
为了一个模式去动它不划算（AGENTS.md 那条规矩）。

## 留了什么 / 关了什么

**留（"他是谁"，少一样江澈就不是江澈）：**
身份、核心性格、内在认知、世界观、世界书、互动对象(用户画像)、私密档案、记忆月度精炼。

**留（"怎么说话"，砍了立刻变模板腔）：**
沉浸感、行为模式、对话质量、格式规矩（含换行符分气泡这条渲染层硬要求）、环境感知、
调取记忆 `[[RECALL:]]`（暮色 10-4 拍板：理思路常常横跨好几次对话）。

**全关的 25 项**逐条登记在 `utils/chatPrompts.ts` 的 `PURE_CHAT_EXCLUDED` 里，
加新功能时对着那张表查。

**关的动作分三层**（`tools` 数组那层最值钱——工具描述每轮常驻在请求体里）：

| 层 | 关了什么 |
|---|---|
| 提示词不注入 | 表情库、思维链、引用、回戳、转账、纪念日、定时发送、唤醒指南、朋友圈、小纸条、信箱、共读、日程、音乐、群聊/Notion/飞书、搜索、小红书、HTML 卡片、麦当劳、心声、角色备忘录、情绪底色、记忆宫殿、双语 |
| **工具定义不传** | `generate_image` / `play_song` / `get_phone_usage` / **全部 MCP** / `propose_cart_items` |
| 不检索 | 记忆宫殿的向量检索本身（不是只不注入，是那次网络往返都省了） |

**没动的：**
- 主动消息 2.0 排程块（`useChatAI.ts:1482` 附近）——它不是"工具"，是角色状态。
  关掉可能让回执不消费、江澈下次重复说。要停他自己关 2.0 开关。
- `chatParser.ts` 解析器——纯聊天靠"不教"就够了。完整模式里那批功能本来也只靠"不教"
  （放歌的文字标记那条路是历史遗留的例外，不在这次范围）。多加一道解析器闸要动共享
  解析逻辑、影响面大，收益不匹配。

## 顺手查实的一件事：用户画像有入口

之前查"用户画像在哪"查错过一次。**它在 `apps/UserApp.tsx:64-71`「个人档案 → 关于我 / 设定」，
直接绑 `userProfile.bio`，写进去就进 prompt**（`context.ts:164-170` 读同一个字段）。

朋友圈里那个「个人简介」是**另一套**：`SocialApp.tsx:155` 注释写明
*"Local - Decoupled from Global UserProfile"*，而且 `:214` 那段只在朋友圈没存过资料时
才回退去读 `userProfile.bio`。两个别搞混。

印象（图里那个紫色卡片）是第三样东西：**角色对用户的看法**，不是"你是谁"。

### 完整模式"一个字节都没变"是怎么保证的

新增的条件全部形如 `xxx && char.chatMode !== 'pure'`，在完整模式下右边恒为 `true`，
条件退化成改动前的样子。**测试里有一条专门钉这个**：
同一份 `chatMode: 'pure'` 的角色，显式传 `full` 时表情库必须回来。

另外测出一个**意外的反向证据**：跑完整模式那条用例时，控制台刷出
`indexedDB is not defined`（来自信箱、共读这些读库的段）。**能刷出这些报错，
说明完整模式路径真的被走到了；而纯聊天那 11 条用例一次都没刷过**——
纯聊天确实一行都没碰那些库。

## 踩的坑（下次别再踩）

**`buildSystemPrompt` 的 `chatMode` 是第 12 个参数。**
`char / userProfile / groups / emojis / categories / currentMsgs / realtimeConfig /
evolvedNarrative / userListeningContext / isListeningTogether / musicCfg / chatMode / ...`

写测试时我少传两个，`'full'` 落到了 `realtimeConfig` 头上，测试红。**项目里已经踩过这个坑**
——`chatPrompts.ts` 的 `chatMode` 参数被放宽成 `string | object` 就是为 22 个错位调用点
兜的底（`isProactive` 的对象传到了 `chatMode` 位置）。**新写调用点时数一遍参数。**

## 缓存：中转站自己就能做，不用走 Anthropic 协议

顺带查实了暮色那个"命中低写入高"的问题。（另立专项，不在这次改）

- 项目**已经没有 Claude 协议**了（`useChatAI.ts:1307` 注释：*任务 2：删 Claude 协议*），
  走的是 `/chat/completions`。代码里**一个缓存参数都不发**——没有 `cache_control`，
  没有 `prompt_cache_key`。
- 站长说的"1 小时缓存"是 Claude 原生端点（`/v1/messages`）的东西，**这条路已经不存在了**。
- 但**中转站令牌设置里的「允许强制缓存」就是干这个的**：New API 识别出是 Claude 模型
  后自己建缓存，前端不用发 `cache_control`。
- **写入率高的根因（推断，待实测）**：中转站只能按整段前缀匹配，而我们发过去的 system
  里塞了一堆每轮都在变的东西——朋友圈、日程、音乐、群聊、记忆宫殿、意识流、最近心声。
  前缀每轮变 → 每次重建缓存 → 钱全花在写入上。
- **怎么一分钟验证**：发一次请求看返回的 `usage`。OpenAI 格式是
  `prompt_tokens_details.cached_tokens`，Claude 格式是 `cache_read_input_tokens`，
  非零就是真在缓存。

**纯聊天对这件事的收益是确定的、且跟命中率无关**：写入的钱按内容大小算，
砍掉一半内容就算命中率仍是零，也要少付一半。
