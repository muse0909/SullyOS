### 清理标准（以后写注释按这个）

暮色反复反馈"加标签"臃肿 + 22:13"为什么写我加的"——**统一规则**：

- ✅ **留**：`为什么这样做`（技术解释，不写时间/谁加的）
  - 例：`// 必须先提取再 sanitize——sanitize 会 strip THOUGHT`
  - 例：`// 3 套协议并存 baseUrl 按 protocol 存不同字段`
- ✅ **留**：`注意危险点`（副作用 / 调用方约束）
  - 例：`// gemini 协议 fetch URL 还没修，先记着`
- ❌ **删**：`暮色 X-X-X 加`（来源 + 日期）
  - 例：`// 暮色 2026-08-06 加：xxx`
- ❌ **删**：`暮色 X-X-X 起的惯例`（日期 + 来源）
  - 例：`// 暮色 2026-07-27 起的惯例：] 单独一行收尾`
- ❌ **删**：`之前 X 这次 Y 因为 Z`（改写对比 / 历史回溯）
  - 例：`// 之前 8-5 改的 8 条太短... 现在：messages 数组 20 条`
- ❌ **删**：`沿用 X-X prompt 模式`（changelog 引用）
  - 例：`// 暮色 8-6 21:35 重写（沿用 7-27 prompt 模式）`
- ❌ **删**：超过 3 行的"上下文"说明
  - 例：5+ 行的"为什么改"说明

### 为什么不一次性清整个项目历代注释

`grep "暮色 2026-08-0[1-6]"` OSContext 找到 17+ 处历史来源标签（8-1 / 8-2 / 8-3 / 8-4 / 8-5 累积），跨多个 commit / 多个 Mavis session。

暮色 22:30 "清吧"——只指**我列的清单**（我 8-6 这一轮加的）。

**不擅自扩范围**：
- 历史标签是历代 Mavis 加的，每个的"为什么"我未必知道
- 清错了可能改坏**其他** Mavis 的逻辑边界判断（注释也是信息）
- 暮色没明说"清整个项目"——只说"清我加的"

**问暮色再决定**：要不要把整个项目的"暮色 X-X-X"标签都清成"为什么"型？（如果清，1-2 个 commit 就能搞定，但范围跨 commit history）

### 注释不是越详细越好

暮色审美"简洁干净清新"——注释也适用。**默认写法**：
- 写代码时**先写代码**，再**写一句为什么**（如果非必要不写）
- 超过 3 行的"说明"——先问自己"这段代码本身不能自解释吗？"
- 改写历史走 changelog（`changelogs/` 目录）——不在代码里留"上次是 X 这次是 Y"

**对比**：
- 改前：`// 暮色 2026-08-06 21:35 重写（沿用 7-27 prompt 模式）：- 角色定位保持...`（5 行）
- 改后：`// 2. Save hidden system hint - 主动消息模式：自动唤醒 + 可调用工具；history 走 messages 数组`（2 行）

**信息密度对比**：
- 改前说"什么时候改的、为什么改、之前是什么样"——这些是**历史信息**，跟当前代码逻辑无关
- 改后说"这段代码做什么、跟其他代码的关系"——是**当前信息**，读代码的人需要的
