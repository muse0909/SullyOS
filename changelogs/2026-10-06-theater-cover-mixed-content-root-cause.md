## 为什么那个改动本身是对的

红果 CDN 相当一部分封面返回 **`image/heic`**，手机不支持。所以改成走短剧库的
`/api/ui/image?url=…`，实测**同一个地址返回 `image/jpeg` 98KB** —— 转码这一步是真有价值的。

**问题出在「转码需要经手电脑」这件事的副作用**，没人预料到：
图片从「公网 https 直链」变成「局域网 http」，而页面源是 https（Vercel）。

**所以旧行为两种都各有毛病：**
- 公网直链：能加载，但一半是 HEIC，手机显示不出来
- 代理路径：全是 jpeg，但混合内容把显示那条路断了

## 真机证据（最硬的一对数据）

暮色 20:19 的诊断截图，同一台手机、同一个地址、同一时刻：

```
手机里存的电脑地址    http://192.168.0.106:8999      ← 对的
地址被内核改写        0 张                           ← 不是自动升级成 https
程序主动去取          成功 · 180ms · 200 · image/jpeg 98107
交给图片框显示        60 张「卡住不动」· 成功 0 · 失败 0 · 还在加载 60
```

**能取到，但显示不出来。** 这一条就把地址、网络、服务端、混合内容自动升级全排除了。

判据的来历值得记一笔：「成功 0 **失败 0**」才是关键 ——
「失败」的定义是「加载结束了但没图」，而这里失败也是 0，说明**没有任何一张加载结束过**，
全卡在 pending。请求发出去了，回音一直没来。不是被拒绝，是够不着/走不通。

## 修法：先取回来再显示（跟视频那条路一样）

新增 `utils/dramaTheater/coverBlob.ts`：

```
fetch(src) → blob → URL.createObjectURL → 喂给 <img>
```

**两边的好处都要了**：取回来的本来就是转好的 jpeg（HEIC 问题解决），
再变成手机本地的临时地址显示（混合内容绕开）。

跟当初放视频的修法一模一样（`1f838f27`），当时的记录写着：
> 「allowMixedContent 只对程序主动取的那条路生效，**显示的那条路安卓内核单独拦**」

——**海报跟视频是同一个坑，视频踩过一次，海报又踩了一次。**

---

## 踩坑 / 需要知道的（重要）

- **去掉图片框自己的懒加载（`loading="lazy"`）。**
  去掉之后进剧场会一次要 60 张，所以 `coverBlob` 自己限并发（6 = 浏览器对同一地址的
  并发连接上限）。
  ⚠️ 但**懒加载跟自己的排队叠在一起会出诡异现象**：排在队里的那些在图片框里
  一直「卡住不动」—— 正是这次查了两小时的现象。别把两个排队机制叠着用。

- **evict blob 缓存时故意不 `revokeObjectURL`。**
  那些图可能正被某个 `<img>` 用着，revoke 掉会让**已经显示出来的图突然变空白**。
  blob 地址在页面会话结束时由内核一起回收，不 revoke 是安全的。

- **诊断模块的 `failed` 判据要写对。**
  我第一版写成「没图就算失败」，结果「成功 0 失败 0」看着像矛盾数据，
  差点误判成统计 bug。加上 `complete` 条件（必须「加载结束了」才算失败）之后，
  三态才是真的：**成功 / 失败（结束了没图）/ 卡住不动（还没结束）**。
  这个区分是这次定位的关键，别为了少写一个条件把它抹平。

- **「混在别的修复里的顺手改动」最危险。**
  `4c7b8547` 的标题是「修 429」，封面逻辑只是夹带在里面。review 时看标题会直接漏掉。
  这跟 `dcc68f6e`（标题「海报全挂（我改坏的）」，但实际只修了 404 那部分）是一对。

- **前两次都修在症状上，而且是**「看起来很像根因**的症状**」**：
  404（地址没拼对）和「组件写在函数体里导致子树重挂」都真实存在、都能自圆其说，
  但都不是不显示的原因。**只有真数据能分开它们。**
