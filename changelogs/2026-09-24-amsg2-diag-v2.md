## 改了什么

排查「后两条 wakeup 任务（20:16 / 20:18）到底从哪来」只能靠代码静态推断，4 个关键盲区。需要补诊断日志。

### 1. `amsgDiag` schema 扩 optional `extra` 字段
- **向后兼容**：旧 reader 读 `extra` 时 JSON 直接保留，不会炸；新 reader 可显式读 extra。
- **写入保护**：值超 80 字 truncate（套用现有 reason 规则）；最多 12 个 key；非字符串值（number/bool/null）原样落。

### 2. 新增 3 个 stage
- `wakeup-trigger-start` — triggerAI 入口，写 `triggerId` + `callSite` + msg 数
- `wakeup-aicontent-snapshot` — 每次 aiContent 重新赋值后 / 工具 followup fetch 后，写 `source label` + contentLen + `containsToken` + rawFirst80
- `wakeup-token-parse-skip` — 同 (charId, fireAt, reason) 60 秒内存 ring 命中跳过时也写，便于看「一次回复内重复」

### 3. triggerAI 头部加 triggerId + callSite
- 接受第三个可选参数 `callSite?: string`，未传记 `'unknown'`
- triggerId 格式 `tr_<base36 时间戳>_<4 字符 random>`（用 Math.random，跟现有 callId 同款，不引入 crypto.randomUUID）

### 4. schedule_next_wakeup 解析处扩展
- `wakeup-token-parsed` 现在带 `rawToken: m[0]`（整段 token 原文 / 不只是 reason 截断 80 字）+ `triggerId` + `parseCount`（同次 triggerAI 第几次解析到，含被 ring 跳过的）
- `wakeup-token-parse-skip` 同样带上面 3 个字段 + `dedupGapMs`

### 5. Chat.tsx 7 个 triggerAI 调用点加 callSite
| 旧调用点 | 新 callSite 标签 |
|---|---|
| listeningTogether useEffect 两处 | `'listeningTogether'` |
| 共读浮窗翻页 | `'coReadSendChapter'` |
| 回溯 (reroll) | `'reroll'` |
| 麦当劳小程序输入 | `'mcdSend'` |
| 记忆宫殿的"触发 AI"按钮 | `'memoryPalaceTrigger'` |
| 输入框右侧闪电按钮 | `'inputBarFlashBtn'` |

### 6. aiContent 重新赋值点（13 处）+ 6 个工具 followup fetch 后 写 snapshot

**主流程（13 处，label = 来源名）：**
1. `main` — 主响应（triggerAI 入场后的第一次 aiContent 赋值）
2. `recall-followup` — `[[RECALL:...]]` 递归 LLM
3. `search-followup` — `[[SEARCH:...]]` 递归 LLM
4. `diary-fallback` — 写日记失败兜底二次 LLM
5. `read-diary-success` / `read-diary-nodiary` — `[[READ_DIARY:...]]` 成功/无内容
6. `fs-read-diary-success` / `fs-read-diary-nodiary` — 飞书 `[[FS_READ_DIARY:...]]`
7. `read-note-success` / `read-note-empty` — `[[READ_NOTE:...]]`
8. `xhs-search` / `xhs-browse` / `xhs-profile` / `xhs-detail` — 小红书 4 种

**工具 followup（6 处，写在 fetch 后立即，不等 fallbackThrough）：**
1. `mcd-propose-N` — 麦当劳小程序 propose_cart_items 工具循环第 N 轮
2. `image-gen-failed-followup` — `generate_image` 失败后 LLM 兜底
3. `image-gen-followup` — `generate_image` 成功后 LLM 确认
4. `play-song-followup` — `play_song` 失败后 LLM 道歉
5. `phone-usage-followup` — `get_phone_usage` 后 LLM 自然回应

注意：MCP 工具调用（line 2268 mcd-propose + 2278 mcp__）走的是 `data = ...` 重赋值，最后 fall through 到 main snapshot，所以它们也会被 main snapshot 抓到。

## 排查流程怎么走

完成这套后，**重置** 诊断日志（角色级弹窗 → 5 个工具按钮里的「查看日志」→ 清空），然后:

1. 触发一次跟"20:14 / 20:15"一样的场景（聊天回合 → AI 回复 → 等等第二条任务出现）
2. 把 `amsg_diag_log_v1` 这份导出（角色级弹窗 → 复制 / 导出 / 或者控制台拿 localStorage）
3. 排查模式:
   - 按时间排序 → 找 `wakeup-token-parsed` 两次
   - 每条 token-parsed 拿 `triggerId` + `parseCount` + `rawToken`
   - 反查最近的 `wakeup-trigger-start`（同 triggerId）确定 callSite
   - 在 triggerAI 同一 triggerId 范围里找 `wakeup-aicontent-snapshot` 的 `containsToken=true` 行，看 source label 是 `main` 还是某个 followup
   - 把这条链:
     `triggerAI(callSite=X) → aiContent snapshot(source=Y, containsToken=true) → token-parsed(triggerId, parseCount=1, rawToken=...) → registerCharacterWakeup → scheduleCharacterTask → wakeup-worker-ack(ok=true)`
   - 第二条任务同 triggerAI 但 parseCount=2 → 看为什么 LLM 在 followup 又输出了一次 schedule_next_wakeup token
