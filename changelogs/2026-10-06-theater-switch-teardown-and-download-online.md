# 切剧继续播上一部 + 追剧「接着看」报没这一集 + 电脑没缓存的剧也能下载到手机

**日期**：2026-10-06
**涉及 commit**：`a943b176` `2e6a77aa`

## 改了什么

用户下午一次报三件事，其中两件是**同一个根因的两副面孔**。

### 1. 切剧时屏幕继续播上一部的内容

根因：`playEpisode` 里只调了 `closeOnline()` —— 那只是把短剧库的在线播放名额还回去，
**跟播放器一点关系都没有**。`blobUrl` 里还挂着上一段视频的地址，
`PlayerStage` 拿到的还是同一个 `src`，所以它的 `useEffect(..., [src])` 压根不触发，
旧流继续拉、继续解码、继续出声。

跟那 4 个名额**没有关系**（用户当时猜是名额的问题，不是）。

做法两层，缺一不可：
- `playEpisode` 在取新片**之前**先 revoke 再置空 `blobUrl`，并立刻挂上加载遮罩
  （不挂的话空 src 那一帧会闪一下旧画面）
- `PlayerStage` 的 `<video>` 加 `key={src}` + `src={src || undefined}`：
  换片就**重建元素**，旧元素从 DOM 摘掉后浏览器随即停掉它的取流和解码，
  新元素不带任何源，什么都不请求

只做前者不够 —— 同一个 DOM 元素把 `src` 改成 `''` 在 Chromium 里会把
currentSrc 落到**文档 URL** 上，反而多发一次没意义的请求。

### 2. 「正在追剧 → 接着看」直接弹「这一集电脑上没有，手机上也没有」

根因：追剧列表的「接着看」按钮硬编码了 `id: ''`
（`playEpisode(w.episode, { id: '', ... })`）。没有剧 id，在线播放这条路整个判死
（`canPlayOnline = !!id && online`、`playEpisode` 里 `d.id && online` 两条判据都是）。

**昨晚修的是另一个入口。** 昨晚把补剧 id 的逻辑写进了 `openEpisodes`（选集页那条路），
而「接着看」是**直接跳播放页**，压根不经过 `openEpisodes`，补 id 的逻辑一次都没跑。

做法：
- 把补 id 抽成 `resolveDramaId(d)`，两个入口共用
- 追剧条目改成传 `w.dramaId`（watchHistory 里 10-06 已经加了这个字段）
- 老条目没存过 dramaId 的，`resolveDramaId` 再按剧名在内存里的剧库兜底查一次
  （1.2 万条全在本地，不是联网搜）

### 3. 电脑上没缓存的剧也能「下载到手机」

原来那个位置是一句**只读提示**「电脑没存 · 在线看」，看着像整部都存不了。
实际不是不能存，是那条路走不通：下载拷的是**电脑下载目录里的文件**，
电脑没这部就没什么可拷。

做法：那个位置换成真能点的「下载到手机（共 N 集）」，点了先排进短剧库的下载队列，
电脑下完**自动接着拷进手机**（只点一下，不用点两下）。

## 动了哪些文件

- `apps/TheaterApp.tsx` —— 抽 `resolveDramaId`；`playEpisode` 切剧时先拆播放器；
  追剧按钮传 `dramaId`；新增「下到电脑」流程（`fetchToMac` + 轮询 + 自动接续 + 10 分钟兜底）；
  选集页那个只读胶囊换成真按钮；加载遮罩加 `loadHint` 区分在线流/手机文件
- `components/dramaTheater/PlayerStage.tsx` —— `<video>` 加 `key={src}` + `src={src || undefined}`；
  新增 `loadHint` prop

## 踩坑 / 需要知道的（重要）

### ⚠️ 同一个 bug 藏在两个入口里，只修一个等于没修

昨晚修「选集页集数点不动」时，把补剧 id 写进了 `openEpisodes`。
今天「接着看」还是同一个症状，但走的是另一条路。
**教训：修「某个地方不生效」的时候，先数一遍有几种入口能到那儿，别只改你手上那个。**
这跟昨天 `canPlayOnline` / `canPlayEpisode` 三套判据只改一套是同一类错误，
一天之内栽了两次同一个坑。

### ⚠️ 关掉「在线会话」不等于关掉「播放器」

`closeOnline()` 这个名字很有迷惑性：它做的是 abort 取流 + 通知短剧库还名额，
**跟 `<video>` 元素没有任何关系**。播放器要单独拆：清 `src` + 重建元素。
两个都得做，只做一个都还在播。

### 为什么不让手机直接从在线流下载

两条路实测对比过：
- **在线流直接下**：一集要实时流完才下完（服务器忽略 Range，回 200 不是 206），
  比电脑直接拉源文件慢好几倍；更要命的是**它占播放名额**，名额总共 4 个
  （`playback_resources.go:39`），拿它下载等于下载期间手机和电脑都看不了剧
- **电脑下载队列**：不占名额。实测电脑上 1126 个集、单集中位 **4 秒**（最长 38 秒）、
  单集 14MB，一部 58 集四五分钟

所以走「先下到电脑，再拷进手机」。顺带这部下完之后还会在「缓存剧库」里躺着，
电脑网页版也能看。

### 10 分钟超时兜底不是可选项

红果源有些集拉不下来（续读 403 / 资源已变化），短剧库会一直重试，
任务永远到不了 success。没有兜底的话按钮永远停在「正在下到电脑 12/58」，
用户只会以为 App 死机了。到点就把已经下到的先存进手机，并说清楚有几集没下下来。

顺带记一个实测数据：**电脑上 1126 个集，`playable` 全是 true，包括 644 个
`status: paused` 的** —— 所以我一度以为「暂停」不等于「没下到」，文件在电脑上、能播。

> ❌❌ **上面那句是错的，15:30 已被推翻 —— 详见下面「更正」。**

## 15:30 加更：下载糊满屏报错的真凶（`playable` 是个会骗人的标志）

### 更正

我写完上面那段**立刻被真机打脸**：用户点「下载到手机」，屏幕上糊了几十条
`Error downloading file`。逐集比对电脑上的磁盘之后：

| 剧名 | 系统记录 | 磁盘实际 |
|---|---|---|
| 咱家剑宗团宠小师妹第二季 | 666 集**全部 playable** | **22 个完整 mp4** + 2 个 `.part` |
| 1987 从中彩票开始崛起 | 81 集 playable | 81 个完整 mp4 ✅ |

**644 个 `paused` 的集，文件压根没落盘。** 我之前只看 `playable` 字段就下了结论，
没去数磁盘 —— 典型的「看字段不看实物」。

顺带把磁盘上的杂项文件也认清楚了（都不该算成集）：
- `.drama-id`：隐藏的剧编号标记
- `023.part.mp4` / `024.part.mp4`：**正在下载中的半截文件**
  （转发服务按 `023.mp4` 去找，找不到回 404 —— 这个行为是对的，半截文件本来就不该给）

### 报错的完整链路

1. 短剧库 `/api/ui/tasks` 的 `playable` 把「已排进队列」和「文件已落盘」混成一个标志
2. App 照着这份名单算「电脑上有 N 集」，把它们全列进要下载的范围
3. 转发服务从磁盘 `listdir` 找文件 → 找不到回 404（实测：1987 第 1 集 200 / 7.87 MB，第 82 集 404）
4. 原生下载拿到 404 抛 `Error downloading file`
5. 每集失败立刻弹一条提示 → 58 集全失败 = 58 条糊满屏，底下要点的按钮全被盖住

### 修法（三层）

1. **转发服务加 `/relay/local/episodes`** —— 直接 `listdir` 下载目录，只认完整的
   `^\d{1,4}\.mp4$`（把 `.part.mp4` 和 `.drama-id` 排除掉）。只数磁盘，这是唯一说真话的地方。
2. **App 侧 `macByDrama` 优先用这份真值** —— 格子着色、「下载到手机（N）」的 N、
   选集范围全部跟着变准。转发服务是旧版（接口 404）时自动退回旧行为，不会把 App 搞挂。
3. **真下之前再逐集探一次**（`Range: bytes=0-0`，只要 1 个字节），
   探不到就跳过，**最后汇总成一条提示**，不再一集一条。

### 教训

**「系统说有」和「东西真在」是两件事。** 一个布尔标志如果被用来推断物理事实，
早晚会说谎 —— 而且它不会报错，只会让你拿着假名单去干真事，然后每一步都失败。
判断「文件在不在」只能直接去问文件系统。

## 备注

- 本轮改过转发服务（`relay.py` 加了一个只读接口），没改短剧库源码
- 「下到电脑」的幂等性没实测（重复排队同一部剧会怎样），因为验证要真下一整部、
  会白耗暮色几百 MB 带宽。接口链路是通的（`handleDownload` → `enqueueDramasAsync`
  → 202 `{"pending":true}`），等暮色真机点一次就知道
- `window.__theaterDiag` 诊断记录还在（本轮没加新的），稳定后要清

## 16:00 加更：下载改成一步到位（用户反馈「整个下载逻辑又有点乱」）

### 反馈原文

> 我想要的是在首页点下载到手机然后就直接下载到手机里。现在这样整个下载逻辑又有点乱。
> 就变成了点一下先缓存到电脑，然后切到缓存剧库再找到这个剧点进去，再点下载到手机，很麻烦啊。
> 还有个能在线播放了缓存到电脑这一步是不对有点多余了？我是说对于手机操作来说。
> 缓存到电脑是不是应该隐藏起来了？点下载到手机就自动一边下电脑一边下手机？
> 手机这边看到的就是直接下到手机了？

### 改了什么

- **下完一集立刻拷一集**，不再是等整部下完再统一拷
- **全程只有一个进度**「已存进手机 x/N」，之前那个「正在下到电脑 12/58」去掉了
- **整套下载选择窗删掉**（区间输入 / 全选 / 全不选 / 体积估算）。
  那个窗是从「缓存剧库」页点「下载到手机」弹出来的 —— 也就是用户抱怨的
  「还得切过去再点一次」。

### 判断依据

**电脑那边先下这一步技术上不能省，但界面上必须省。** 往手机拷的就是电脑磁盘上的
文件，电脑没有就没什么可拷 —— 这是 `downloadEpisodeToPhone` 只吃 URL 决定的。
但用户看到的应该是「直接下到手机」，所以：

| 阶段 | 用户看到的 | 实际在干嘛 |
|---|---|---|
| 电脑在下的那几秒 | 进度条 0%（文字不动） | 短剧库后台拉源文件 |
| 电脑下完第 1 集 | 1/N | 立刻拷进手机 |
| 第 2 集落盘 | 2/N | 立刻拷进手机 |

所以「缓存到电脑」不是多余，是**不可见的内部实现**。之前把它暴露在 UI 上
（按钮写「正在下到电脑 12/58」、下面还挂一行小字「先下到电脑，再存进手机」），
用户自然觉得流程多了一步。

### 主循环怎么写的

`phoneDl` + 一个 1.2 秒的定时器：每轮问一次转发服务「磁盘上现在真有哪些集」，
挑出**新的、手机里还没有、这次没失败过**的最小那一集，拷过来。一次只拷一集 ——
同时下好几集会把 WiFi 带宽吃满，失败时也不好定位是哪一集（电脑下单集只要 4 秒，串行够快）。

两个必须记住的坑：
- **定时器的闭包会一直拿着 effect 建立那一刻的 `phoneDl`**，`saved` 永远停在初始值，
  同一集会被反复挑中。必须用 `phoneDlRef` 读最新值。
- **拷之前先 `setPhoneDl` 把这一集占进 `saved`**，成功失败都算占住，失败另进
  `phoneDlSkip`。不先占住的话下一轮又会挑中同一集，卡死在这一集上。

超时兜底：10 分钟没往手机里存进新的一集就收工（红果源有些集拉不下来，
短剧库会一直重试，不设兜底会永远停在某个数字上）。

### 死代码清理

重构完这些没人用了，一并删掉：`downloadEps`、`avgPhoneEpBytes`、`saveAll`、
`saveAllCancel`、`probeLocalEpisode`（逐集探测改成一次拉全量列表了）、
`DownloadPicker` 组件、选择窗的三个 state。

### ⚠️ 还没定位的问题

15:44 推的版本已经在手机上跑起来了（转发日志里能看到 11 次 `/relay/local/episodes`
调用，说明部署成功），但用户随后报**「打开点剧集报错」**。
翻了两边日志都没找到异常：转发 15:45 开会话返回 200，短剧库侧干净。
**没拿到截图，App 侧还没定位到** —— 本轮一起验。

`origin/master` 仍是 `ef17e1aa`，全程未动。

## 17:05 加更：`mine is not defined` 崩掉整个选集页（我的错）

### 现象

17:03 打开剧场 → `ReferenceError: mine is not defined` → 整个页白屏，
顶栏挂红色 SYSTEM ERROR。

### 根因

上一轮重写下载流程时，我把

```jsx
{(() => {
  const mine = phoneDl?.title === picked.title ? phoneDl : null;
  ...
  return <Pill>...</Pill>;      // ← 按钮这段能用 mine
})()}
{/* 进度条这段在函数外面，也写了 mine → ReferenceError */}
{mine && <div className="进度条">…</div>}
```

`mine` 只在那个当场执行的小函数里可见，进度条在外面够不着。**一进选集页就抛。**

### 为什么 build 没拦住 —— 这才是真问题

`package.json` 里 **`"build": "vite build"`，没有 `tsc`**。
esbuild 只转译不做检查，作用域错误、类型不匹配它统统不管。
所以「跑一下 build 通过了」在这里**不等于**代码没问题。

### 修法

1. `mine` 提到 return 之前、跟其它值同一层级
2. 加类型检查：
   - `npm run typecheck:theater` —— 只查剧场这几个文件，退出码 0 = 干净
   - `npm run typecheck` —— 全量（这个项目历史包袱几百条错，只当参考）
3. 顺手修掉 `pullLocalEps` 里两处 `string | undefined`
   （`filter(t => t.dramaTitle)` **不会**让 TS 收窄，要写类型守卫 `filter((x): x is string => !!x)`）

规矩写进 `AGENTS.md` §4.3 了。

### 附带说明：第一张图那个 `Failed to fetch` 不是独立故障

它报的是 `/relay/local/episodes?drama=重生扬子鳄…`。翻日志：
转发服务是 `ThreadingHTTPServer`、进程一直在、15:44 那次 11 个请求全是 200。
所以它只是**页面崩了，顺手把正在飞的那个请求打断了**。根因还是 `mine`。

### `typecheck:theater` 脚本自己写错了

第一次写的是：

```bash
test -z "$(tsc … | grep -cE '…')"
```

**`grep -c` 无匹配时输出的是 `0`，不是空字符串** —— 所以 `test -z "0"` 永远为假，
退出码永远是 1。刚才差点被这个假报警带偏。改成 `tee` 落文件 + `test ! -s`。

这类「判断逻辑本身写错」的错误和 4.1 那个是同一类：**看着在验证，其实是错的**。
以后写了自动化检查，先手动确认它在「应该失败」时真的会失败。

## 18:20 加更：选集真能选 + 并行请求打满队列（`f125ed6e`）

### 1. 「还是只能整部下载」

> 反馈原文：「下载这个加了弹窗，但是还是只能整部下载呀。
> 这个想改成电脑上下整部，但是手机上选几集就下几集？」

上一版把「电脑上一集都没有」退化成一个「整部下」按钮——正好是他不要的。

按他的原话拆开做，**这两件事本来就不该绑死**：

| 谁 | 下什么 |
|---|---|
| 电脑 | **整部**（那是短剧库自己的任务队列，用户不关心也不该等） |
| 手机 | **只拷选中的那几集**，拷完就停 |

所以 `openDownloadPicker` 里，电脑上一集都没有时，
可选集用**全剧集号**（`1..total`），弹窗照常能勾、能输区间 2-20、能全选。
一集都没勾 = 不下，不偷偷变成整部。

### 2. `Failed to fetch`（17:11:36）

翻转发服务 220 行日志：

| 时间 | 请求 | 结果 |
|---|---|---|
| 17:11:36 | Cannibal 那部的 `/relay/local/episodes` | **服务器压根没有记录** |
| 17:11:37 | 其它 11 个 `/relay/local/episodes` | 全部 **200** |

没有 4xx、没有 5xx、没有异常。**服务器没记录 = 请求根本没离开客户端。**

原因：`refresh()` 里对电脑上 11 部剧 `Promise.all` 并行发，
而同一次刷新里还有一个 **21 MB** 的剧库列表要转发，连接队列打满，
多出来的那个请求直接被拒。

改成：

- **串行**（本地网络一个几十毫秒，11 个也就不到一秒）
- **不 await**，放后台跑，不拖住首屏
- `openEpisodes` 里再单独拉一次「当前这部剧」，保证这一部的格子一定准

### 🔑 排查判据（写进教程了）

> **服务器日志里没有这条请求 = 请求根本没离开客户端。**

这一刀把「服务端问题」和「客户端问题」分开，省掉在服务端翻半小时日志。
教程里加了一张对照表：

| 现象 | 往哪查 |
|---|---|
| 服务器日志没有这条请求 | 客户端：队列满 / URL 错 / 被预检或混合内容拦 / 超时 |
| 有记录，返回 4xx/5xx | 服务端：路径、权限、上游状态 |
| 返回 200 但客户端读不到 | `Access-Control-Expose-Headers` 没列这个头 |
| 偶尔失败、并发时更容易 | 队列打满 → 改串行 |

## 18:30 加更：在线播放拖进度条崩（`a5d58846`）

### 现象

真机 18:25，点一下进度条就抛：

```
TypeError: The provided double value is non-finite.
    at onPointerUp (PlayerStage)
```

### 根因（一行）

```js
if (v.duration) setDur(v.duration);     // ❌
```

在线流走 MediaSource 边下边播，`video.duration` 是 **`Infinity`**。
而 **`Infinity` 在程序里是「真」** —— 所以这行判断放行了，
「无限」被存进了 `dur`。

后面拖进度条：

```js
const pct = min(1, max(0, (clientX - left) / width));
return pct * dur;              // 拖中间 = Infinity，拖最左 = 0 * Infinity = NaN
v.currentTime = t;             // ❌ 两种都不是合法数字
```

### 为什么之前没发现

`fmtTime()` 里有 `isFinite` 检查，所以界面上显示的是「0:00」——
看着只是「时长不准」，实际是**一拖就崩**。
（这条本来就在 todo 里挂着，当时以为只是显示问题。）
**显示层挡住了症状，掩盖了底层是崩的。**

### 修法：三道防线

1. 抽 `durOk(x) = Number.isFinite(x) && x > 0`，元数据和 timeupdate 两处都走它
2. `seekTo` 算完再验一次 `isFinite(t) && t >= 0`，不合格返回 `null`
3. `onPointerUp` 赋值处 `try/catch` + 有限性检查（有些内核 seek 越界也会抛）

### 顺带的产品决策：时长未知就不给拖

画一条拖不动的进度条，用户只会以为坏了。
改成写「已播 x / 边下边播」，条保留但不画滑块、不响应拖动。

### 通则（写进教程了）

> **任何从媒体 / DOM API 拿到的数字，赋给别处之前都要过一遍 `Number.isFinite`。**
> `NaN` 和 `Infinity` 都不是 `null`，`||` 和 `if (x)` 都挡不住它们。

## 19:00 加更：反复 429 的真凶 + 五个问题（`4c7b8547`）

### 🔴 1. 播放名额泄漏 —— 反复 429 的根因

真机 18:48 报「播放位满了」，点「清空播放位」说失败。复现数据：

| 第几次开 | 结果 |
|---|---|
| 1 | 成功 |
| 2 | 成功 |
| **3** | **429** |
| 随后 `closeAll` | **返回 4** |

说明：之前有 **2 个残留会话**，且实际可用名额只有 **2 个**。

根因在 `fetchEpisodes()`：

```ts
// ❌ /api/ui/playback/open 开的是「真的播放会话」，不是只读的查集数接口
const r = await fetchEpisodes(addr, id);
if (r.total) setEpTotal(r.total);
// r.session 没人管 —— 每进一次选集页漏一个名额
```

**每进一次选集页就漏一个名额**，进几次就再也开不出新片。
只有 1 分钟超时能救，但那是在等泄漏自己消失。

修：拿到 `session` 就在 `finally` 里关掉（成功/失败/中途切走都得还）。

顺带两件事：
- `closeAll` 返回 0 **不是失败**，意思是「本来就没有占着的」。之前一律判成失败并
  `return`，用户点了没反应、白等一场。真失败是请求压根发不出去（已在上游抛异常）
- 名额实测只有 **2 个**（默认设的是 4），`mediaResources` 的 snapshot 逻辑待查

### 2. 海报一半空白 —— 红果封面是 HEIC

| 剧 | CDN 直连返回 |
|---|---|
| 180万之征地风云 / 1991从柴房到天明 / 24小时紧急营救 | **`image/heic`** ❌ |
| 1982药神觉醒 / 1984我来当家 / 1987从中彩票开始崛起 | `image/jpeg` ✅ |

安卓 WebView 不支持 HEIC。同一个地址**走短剧库图片代理一律返回 jpeg**。
修：`coverUrl` 优先用短剧库的代理路径（`/api/ui/image?url=…`），渲染时 `coverSrc()` 拼转发地址。

### 3. 退出演场就该还名额（用户原话：「返回了还占着播放位？」）

之前只有两个时机：切集时（`playEpisode`）和整个页面被回收时（`pagehide`）。
中间漏一大段：按返回回选集页、点标题栏回聊天页、打开选集抽屉挑另一部 —— 全都一直占着。

改成靠 `page !== 'player'` 触发，**少一个入口就少一处漏**。

**用户问「改成 3 秒行不行」→ 不用。** 泄漏修好就不会满；3 秒会把正常看的也杀掉。

### 4. 接着看真的接着看

`recordWatch` 存了 `position`，播放时压根没用 —— 三种来源都从 0 开始。
PlayerStage 加 `resumeAt`：这一集第一次 ready 时跳一次（250ms 后），用户拖过之后不再插手。
在线流时长未知（`Infinity`）跳不过去。

### 5. 缓存剧库长按移走 + 顶部返回按钮

- 长按用 **touch 计时 500ms**，不用 `onContextMenu` ——
  安卓上长按会先弹系统「复制/保存图片」，那一下就把事件吃掉了
- 只写 localStorage（`theater_mac_hidden`），**不碰电脑上的文件**；全移走时给「全部恢复」
- 标题栏返回按钮走 `closeApp()`，回聊天页（OSContext 有 parent 机制）

### 6. 类型检查今天第三次救场

编辑 `MAC_HIDDEN_KEY` 时顺手删掉了 `MAC_FETCH_TIMEOUT`（以为没用了），
代码里还在用 → `typecheck:theater` 直接报出来。
这个脚本 10-06 当天已经抓到三次真问题了（`mine`、类型不匹配、这次的常量）。

## 19:25 加更：海报全挂（我改坏的）+ 三个 UI 问题（`dcc68f6e`）

### 1. 🔴 海报从「个别不显示」变成「全都不显示」—— 我的锅

上一版（`4c7b8547`）为了修 HEIC，把 `coverUrl` 改成短剧库的代理路径
（相对路径 `/api/ui/image?…`），然后**只在 `macItems.map` 那一处**调了 `coverSrc()` 拼地址。

剧库首页的 items 直接把相对路径塞进 `<img>`，被浏览器当成本站路径解析成
`https://sully-os-git-fix-…/api/ui/image?…` → **404**。
缓存剧库那处虽然拼对了，但两边一起看就是「全都不显示」。

**修：拼地址这一步下沉到 `Grid` 渲染里统一做**，各处只管传原始 `coverUrl`。
一处拼、全都对，漏一处不可能了。

> 教训：**同一个转换不要分散在多处**。修 A 处顺手改了数据结构，就得把所有用到它的地方
> 一起过一遍 —— 我改了 `mapDrama` 的输出格式，就只记得改一个 map。

### 2. 「封面上的字一闪一闪」

图片 404 后内核反复重试的样子。加了 `CoverImg`：**失败一次就换成占位图标，不再重试**；
`src` 变化时重置失败标记（否则换剧时被上一张的失败判死）。

### 3. 返回按钮回的是桌面，不是聊天页

`closeApp()` 回的是 `parentApp`，而剧场这个入口历史上没设过 parent，
所以落到 Launcher = 回桌面。改用 `jumpToChat(activeCharacterId)`，
直接回打开剧场时所在的那个聊天。

### 4. 进度条被挡、最右边全屏按钮看不见

黑色那块是**错误提示卡片**（`absolute inset-0` 铺满整个播放区），
控制条叠在它上面就成了「卡片盖住半个进度条」。

修：**出错时不画控制条**（跟 loading 时一样）。
出错了用户要的是「重试」这一个动作，不需要同时给他一条拖不动的进度条。
控制条另加 `z-10` 兜底。

- 恢复提示移到网格**最底下**：`已移除剧集可搜索重新下载恢复`
