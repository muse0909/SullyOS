## 为什么只给纯聊天

不是随便定的，是纯聊天的 system 段真的稳定。

纯聊天 = 身份 + 性格 + 内在认知 + 世界观 + 世界书 + 用户画像 + 记忆月度，
全是静态文本，逐字不变 → 每轮都能命中同一段前缀。

完整模式的 system 段塞着日程时段（按当前时间算）、最近心声（带「X 分钟前」时间戳）、
朋友圈/日记/小程序这些每轮都在动的内容 → 前缀一变后面全废，
开缓存等于每轮白付一次写入费（5/M，是普通输入 4/M 的 1.25 倍）。

7-18 那次「4 次写入 0 次读取」就是这么来的。纯聊天把这些全关了，前缀才真的稳。

硬门在 `useChatAI`，判据写 `char.chatMode === 'pure'`，不是靠 UI 藏起来。

## 三档怎么设计的

`off | 5m | 1h` —— 这三个就是 Anthropic 官方 `cache_control` 支持的全部值，没有第四种。

- 默认 `5m`（暮色明确选的）
- `off` 产出 `null`，调用方不挂这个键，请求体跟现在一模一样
- 存 localStorage `sullyos_chatCacheTtl`，不进 `apiConfig` —— 它不是 API 连接信息，
  跟着角色走没道理；也不进备份导出（跟密钥无关，换设备重选一次就行）

## 踩坑 / 需要知道的（重要）

- **`isPureChat` 在这里会 TDZ**。`useChatAI` 里 `isPureChat` 是 1738 行才声明的，
  而挂断点这段在 1343 行。必须写 `char.chatMode === 'pure'`，跟文件里 1279 行那处同一把尺。

- **不能留 `cache_control: null`**。所以用展开语法：
  `...(pureChatCacheControl ? { cache_control: pureChatCacheControl } : {})`。
  留 null 键 newapi 可能报错。

- **`buildCacheControl` 必须每次 new 一个新对象**（这条是测试逼出来的真 bug）。
  原来直接 `return TTL_TO_EPHEMERAL[ttl]`，返回的是模块级常量表里那一份。
  挂进请求体后任何一层顺手改了这个对象，就会污染常量表，之后每轮都拿着改坏的
  cache_control 发出去。已改成 `{ ...TTL_TO_EPHEMERAL[ttl] }`。

- **必须实测有没有真生效**。这是最大的一个未知。
  7-18 那次 1 小时「生效过」是在 `/v1/messages` 端点上；
  同日 `bc7034b9` 记录：切到该端点 curl 验证，cache_creation / cache_read 始终是 0，
  站长当时也说「走 openai 接口不能加 claude 字段，会被 newapi 丢弃」。
  现在站长说「5/1h 都能，酒馆打 1h 断点就行」—— 可能是他那边修了，也可能是别的写法。
  **所以不能假设开了就有用。**

- 为此在 API 请求日志里加了两个字段，方便暮色一眼判断，不用猜：
  - `cacheTtlRequested` —— 设置里选的档
  - `cacheApplied` —— 这次请求体里实际挂上的值（非纯聊天一律 `off`）

  流程：发一轮 → 控制台 `copy(JSON.parse(localStorage.getItem('sullyos:lastApiReqLog')))`
  → 看 `cacheApplied` 是不是 `5m`/`1h`（是 = 标记确实发出去了）
  → 再看中转站日志「缓存读取」是不是非零（非零 = 真命中）
  → 读取一直是 0 就切回 `off` 档，跟以前一样不亏。

- **默认 5m 对暮色的用法大概率是亏的**。他一条消息十几分钟，5 分钟必然每轮超时重写。
  这不是默认值出错，是他明确选的，想要省钱自己切 `1h`。UI 提示里写清楚了这一点。

- **两个错别记的账**（免得下次再犯）：
  1. 我曾说「时间戳导致前缀变化」—— 那是完整模式的东西，纯聊天下记忆宫殿关着，不存在。
  2. 我曾拿「请求体 JSON 从 15,054 字符压到 11,812」当省了多少的证据 —— 错。
     那是浏览器序列化出来的长度，中转站在后面还会加它自己的东西，两边加的不在一个位置，
     **这两个数字不能相减**。真实对比只能看中转站账单上的 token 数。
